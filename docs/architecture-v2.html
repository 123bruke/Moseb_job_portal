3. Roles and user flows

Candidate

  1. Sign up (Supabase): name, email, password, nationality, phone, location.
  2. Profile: skills, years of experience, education, domain, languages, expected salary.
  3. Job feed is ranked by profile experience and skills (Section 7).
  4. Apply to a job: fill the application form and upload a resume (PDF/DOCX).
  5. See own application status and AI feedback (missing skills, improvements).

Company

  1. Sign up as company, create a company profile.
  2. Post job: title, description, required skills, min experience, education, deadline, number of seats, plus an optional requirement file (PDF/DOCX/TXT with any extra requirements).
  3. When the deadline passes (or the company clicks Close and Rank), the system ranks all applicants.
  4. The company receives the Top-N shortlist with reasoning and comparison.
  5. After delivery, non-selected candidate data is removed (Section 9).

Admin

Manage users, view audit log, monitor queues and model costs.

4. Ingestion pipelines

4.1 Resume pipeline (async worker)

Upload -> Supabase Storage -> queue job
 1. Validate (type, size, virus scan, page limit)
 2. PDF reader: PyMuPDF text per page; OCR fallback if scanned
 3. YOLO layout detection (page images):
      - classes: header, photo, table, section-title, skills-block, signature, logo
      - use: crop sections, drop photo/logo noise, order the reading flow of multi-column CVs
 4. Section parser (Gemini, structured output): name, contact, skills, experience entries,
    education, certificates, languages, projects
 5. Normalize: skill aliases (JS = JavaScript), compute total years of experience
 6. Save structured result -> Postgres
 7. Chunk by section + embed (Gemini embeddings) -> ChromaDB (collection: resumes)
 8. Upsert graph -> Neo4j (Candidate)-[:HAS_SKILL {years}]->(Skill)
 9. Mark application "processed"

4.2 Job pipeline

Post job (+ requirement file)
 1. Extract text from the requirement file (same PDF reader)
 2. Gemini converts everything into a structured rubric:
      must-have skills, nice-to-have skills, min years, education, certifications,
      weights (e.g. skills 40 / experience 30 / education 10 / domain 10 / other 10)
 3. Company can review and edit the rubric before publishing (human in the loop)
 4. Save to Postgres, embed to ChromaDB (collection: jobs), upsert graph (Job)-[:REQUIRES]->(Skill)

5. Matching and ranking engine

Hybrid scoring: not only an LLM guess.

Signal Source Weight (default, editable per job)
Must-have skill coverage Postgres + Neo4j 35%
Semantic similarity (resume chunks vs job requirements) ChromaDB 25%
Experience fit (years, seniority, domain) Postgres 20%
Education and certificates Postgres 10%
Graph proximity (related skills, e.g. FastAPI is close to Flask) Neo4j 10%

Hard filters first: missing a must-have, below minimum years, or wrong location or work-authorization (if the company set it). A candidate who fails a hard filter is marked "not eligible" with a reason, not silently dropped.

Ranking: weighted score 0-100, then Gemini does a pairwise comparison of the top ~10 candidates (candidate A vs B on this job), which breaks ties and produces the comparison text.

6. Reasoning system (explainable)

An agent graph (LangGraph on top of LangChain) with these nodes, each writing a visible step to reasoning_traces:

flowchart TD
  A[1 Understand job rubric] --> B[2 Retrieve evidence from resume - Chroma]
  B --> C[3 Verify each requirement: met / partial / missing + quote]
  C --> D[4 Score with formula + graph signals]
  D --> E[5 Compare against other candidates]
  E --> F[6 Self-check: bias and hallucination review]
  F --> G[7 Final explanation + recommendation]

Rules that keep it trustworthy:

  • Evidence-grounded: every "met" claim must cite a resume chunk. No evidence means "missing".
  • Bias guard: the scoring agent never sees name, photo, age, gender, nationality. Those fields are stripped before step 2. (Nationality is stored for the profile, not used for ranking.)
  • Self-check node flags contradictions (e.g. "10 years" claimed but the dates give 3).
  • Output per candidate: score, per-requirement table, strengths, gaps, risk flags, one-paragraph reasoning, confidence.
  • Company sees the trace, can override ranking, and overrides are logged.
  • Your old PASS/FAIL classifier becomes just one cheap pre-filter, not the decision maker.

7. Job feed for candidates (recommendation)

  1. Candidate generation: Neo4j query: jobs whose required skills overlap the candidate's skills, within experience range.
  2. Semantic boost: Chroma similarity between the profile and job embeddings.
  3. Rank: 0.5 skill-overlap + 0.3 semantic + 0.2 experience-fit, plus "recently posted" tie-breaker.
  4. Explain: each card shows "Matches 7 of 9 skills; you are 1 year short on experience".
  5. Learning loop: clicks, applies and saves update graph edge weights.

9. Delivery and cleanup ("send best fits, remove the rest")

  1. Ranking finishes and the shortlist report is generated (PDF + in-app view).
  2. Shortlisted candidates' full data is delivered to the company.
  3. Notify everyone of the outcome (selected / not selected).
  4. Cleanup job (scheduled): for non-selected applicants, delete the resume file, Chroma chunks, and graph resume edges. Keep a minimal record (application id, status, timestamp) for audit.
  5. The candidate is told at apply time, via a consent checkbox, that the resume is deleted after the decision. Add a configurable retention period (e.g. 30 days) and a "delete my account and data" button. This matters legally (GDPR-style rules) because you store personal data from many nationalities.

  • Edges: HAS_SKILL{years,level}, REQUIRES{importance}, POSTED_BY, IN_DOMAIN, RELATED_TO{weight} (skill to skill), APPLIED_TO, VIEWED, SAVED
  • Seed RELATED_TO from your domain JSONs.

15. CI/CD (GitHub Actions)

ci.yml (on every pull request and push)

  1. Backend: lint (ruff), type-check (mypy), unit tests (pytest), coverage gate
  2. Frontend: lint, type-check, unit tests (Vitest), build
  3. Integration job: start Docker Compose test stack (Chroma, Neo4j, Redis) and run API tests with a mocked Gemini
  4. Agent evals: small labeled set of resume-job pairs, fail the build if ranking accuracy drops below threshold
  5. Build Docker images and scan them (Trivy)

security.yml: dependency audit, secret scanning, CodeQL (weekly).

cd.yml

  • Merge to main: build and push images to GHCR, deploy to staging, run smoke tests
  • Git tag v*: manual approval, deploy to production (VPS with Compose over SSH, or Cloud Run / ECS), run DB migrations first, then roll out; automatic rollback if /ready fails

Branching: feature/* to PR to main to tag.

17. Security and compliance checklist

  • Verify the Supabase JWT on every request; enforce roles in dependencies
  • RLS on all tables; the service-role key lives only in the backend/worker
  • Upload limits, MIME sniffing, malware scan, filename sanitizing
  • Prompt-injection defense: resume text is treated as data, never instructions; the system prompt tells Gemini to ignore commands inside documents
  • PII never logged; encrypt files at rest; signed URLs with expiry
  • Rate limits on apply and chat endpoints; Gemini cost caps per day

18. Build order (milestones)

  1. M1 Foundation: repo layout, Docker Compose, FastAPI skeleton, Supabase auth + roles, CI lint/test
  2. M2 Data: Postgres schema and RLS, Chroma and Neo4j connections, seed knowledge JSONs
  3. M3 Company side: post job, requirement file, rubric editor
  4. M4 Candidate side: profile, job feed, apply form, resume upload
  5. M5 Ingestion: PDF reader, YOLO layout, section parser, embeddings, graph upsert
  6. M6 Ranking and reasoning: scoring engine, agent graph, comparison, traces
  7. M7 Delivery: shortlist report, notifications, cleanup job
  8. M8 Hardening: evals, security checklist, CD to staging then production

Notes / assumptions

  • YOLO needs labeled CV layouts to train (about 300-500 pages is enough to start); until then, run without YOLO and rely on PyMuPDF with OCR fallback.
  • Gemini is the only LLM; model names are in env vars so you can swap versions without code changes.
  • Auto-ranking should support hiring decisions, not make them alone. Keep the company override and the reasoning trace visible.
